Durable execution for PHP: one method, resumable by replay.

Get started

A payment is charged, then the process must reserve stock, then email the customer. The worker is redeployed between the second and third step. What happened to the order?

Without Durable — the same redeploy
charge The job is retried from the top. The customer is charged a second time.
reserve-stock Held for an order that will never ship — or dropped, and oversold.
send-receipt Never runs. The customer hears nothing at all.

You find out from a support ticket three days later, and the way back is a repair script written by hand, in production.

With Durable — the same redeploy
charge Returns from the journal. Charged exactly once.
reserve-stock Returns from the journal. Reserved exactly once.
send-receipt Runs once, after the restart. The email goes out.

Nothing happened to it. The charge is not replayed, the reservation is not lost, and the email still goes out.

One method, top to bottom

On every resume the code re-runs from the start, but each step already recorded returns its recorded result instead of running again.

There is no state machine to declare and no transition table — the process is the method. The environment is injected in the constructor, and activities are typed stubs, so every call your workflow makes is one your IDE and your static analyser already understand.

A worker can be redeployed mid-process and the execution continues where it stopped.

src/Workflow/CheckoutWorkflow.php PHP 8.2+ · hover a line
#[Workflow(name: 'checkout')]
final class CheckoutWorkflow
{
private ActivityStub $orders;
 
public function __construct(
private readonly WorkflowEnvironment $env,
) {
$this->orders = $env->activityStub(OrderActivities::class);
}
 
#[WorkflowMethod]
public function run(string $orderId): string
{
$payment = $this->env->await($this->orders->charge($orderId));
$this->env->await($this->orders->reserveStock($orderId));
$this->env->sleep(Duration::minutes(5));
$this->env->await($this->orders->sendReceipt($payment));
 
return $payment;
}
}

What you no longer write

Five moving parts you maintain today, and the single thing that answers each one instead.

What you delete What answers it now
−A state column, and the migration that adds the next state +The line the method is on. The journal holds the position.
−A cron that scans rows in pending_* +The next statement. Timers and signals wake the execution.
−A retry counter and the dead-letter table +RetryLimit::ofAttempts(3) — an option on the stub.
−A guard against the job that ran twice +A recorded step returns its recorded result. It cannot run twice.
−A way to know why order 4242 stopped three days ago +Replay its journal: every step, every result, every attempt.

Five files and a runbook, replaced by one method and the journal behind it.

Six things you will need next

Every excerpt below is the same class as above: the environment injected in the constructor, activities as typed stubs. Each one has its own page.

use case 01

Run two steps at once, and keep both results

Calling an activity returns an awaitable, not a result. all() assembles two of them into one; await() is where the execution actually waits.

Parallelism →
two activities at onceboth results
[$stock, $credit] = $this->env->await($this->env->all(
    $this->orders->reserveStock($orderId),
    $this->orders->checkCredit($orderId),
));
use case 02

Bound a wait in time, without writing the race

The deadline is the second argument to await(): when it elapses you get a failure, not an ambiguous null. Waiting for the clock alone is just sleep().

Deadlines and timeouts →
a deadline on the awaitelapsed is a failure, not a null
try {
    $quote = $this->env->await(
        $this->orders->callProvider($orderId),
        Duration::seconds(30),
    );
} catch (DeadlineExceededException $e) {
    $quote = $this->fallbackQuote($orderId);
}

$this->env->sleep(Duration::minutes(5));   // just wait — awaits for you
use case 03

Take the answers that are enough, drop the rest

Three quotes out of eight are enough to decide; the other five cost only their latency. Results come back indexed by declaration position, so every price still points at the provider that gave it.

Quorum with some() →
the first three answers winresults indexed by declaration position
$prices = $this->env->await($this->env->some(3, ...$providers), Duration::seconds(2));
use case 04

Decide what a failure means, once

Retry limits, non-retryable exceptions and per-attempt timeouts are options on the activity stub — not a counter, a dead-letter table and a runbook spread across your codebase.

Retries and failure policy →
options on the stubdeclared once, in the constructor
$this->orders = $env->activityStub(
    OrderActivities::class,
    ActivityOptions::of(
        retryLimit: 3,
        timeouts: Duration::seconds(30),
        nonRetryableExceptions: [PaymentRefusedException::class],
    ),
);
use case 05

Let the outside world interrupt a running process

A signal delivers input to an execution already in flight; a query reads its state without disturbing it; an update is validated and answers back. Approval steps and manual holds stop being separate infrastructure.

Signals, queries and updates →
signal, query, updatetalking to a live execution
#[SignalMethod(OrderSignal::Approve)]
public function approve(string $approver): void { /* … */ }

#[QueryMethod('status')]
public function status(): string
{
    return $this->status;
}

#[UpdateMethod('changeAddress')]
public function changeAddress(string $address): string { /* … */ }

// inside the workflow method — a plain string still works:
$approval = $this->env->waitSignal(OrderSignal::Approve, Duration::hours(1));
use case 06

Undo what already happened when a process is cancelled

Cancellation arrives inside the workflow as a catchable failure, so the process can compensate — refund the charge, release the stock — and then stop for real.

Cancellation and compensation →
cancellation you can catchcompensate, then let it through
try {
    return $this->env->await($this->orders->charge($orderId));
} catch (WorkflowCancelledFailure $e) {
    $this->env->await($this->orders->refund($orderId));

    throw $e;
}
in practice 01

A process that lasts a month, in one method

An order goes to a supplier. The supplier has 48 hours to confirm, or it escalates. Once confirmed, delivery is awaited for up to 30 days, with reminders at day 7 and day 21. If nothing arrives, the payment is refunded. Below is the whole of it.

one method · 48 hours, then 30 daysno status column, no cron tick
try {
    $this->env->waitSignal(SupplierSignal::Confirmed, Duration::hours(48));
} catch (DeadlineExceededException $e) {
    $this->env->await($this->desk->escalate($orderId));
}

$this->env->sleep(Duration::of(new \DateInterval('P7D')));
$this->env->await($this->mail->remind($orderId));

$delivery = $this->env->waitSignal(
    SupplierSignal::Delivered,
    Duration::of(new \DateInterval('P30D')),
);
01

Racing a human against a clock

In Messenger, “confirm within 48h or escalate” needs two things in flight — a delayed message and a webhook — plus a way to know which won and to cancel the loser. The trap is the edge: the supplier confirms at 47h59 and the deadline message fires anyway. Who decides? A deadline that is a typed failure rather than a value is what makes that expressible at all.

02

Waiting costs nothing

Thirty days in a queue is a message parked in a broker that has its own TTLs and redeliveries. Thirty days in cron is a row scanned every tick for a month. Here the execution is simply not running, and the next line waits for it.

03

Local variables die at the end of a handler

Everything computed in step one must be persisted to exist in step four, so the process becomes a status column plus a context table — and every new step is a migration. In one method, $delivery is just a variable.

04

“Why has order 4242 been stuck for three days?”

With cron or handlers you reconstruct the answer from logs. Here you replay the journal: every step, every result, every attempt, in order.

Being fair

Messenger and cron can do all of this. That is the point — you watch them do it, with status columns, locks and guards against double processing. The comparison is about what you have to write and keep, not about what is possible.

in practice 02

Orchestrating an AI agent, with Symfony AI

An agent is a loop of non-deterministic decisions that cause irreversible effects. That is exactly the pair replay makes dangerous — and the journal is what resolves it.

a tool, and the turn around itthe model call is an activity
#[AsTool('issue_refund', 'Refunds an order, in cents')]
final class IssueRefund
{
    public function __invoke(int $orderId, int $amount): string { /* … */ }
}

// In the workflow: the model call is an activity, never inline —
// it answers differently every run, and replay must see the same answer.
$plan = $this->env->await($this->agent->decide($conversation));

if ($plan->needsApproval()) {
    $this->env->waitSignal(AgentSignal::Approve, Duration::hours(24));
}

$outcome = $this->env->await($this->tools->run($plan->tool(), $plan->arguments()));
01

The model does not answer the same thing twice

Under replay the workflow must see the same answer, or it walks into a different branch and the history lies. So the model call is an activity, not inline code. This is not an implementation detail — it is the condition for an agent to be resumable at all.

02

A tool call is a side effect

issue_refund refunds for real. If the worker restarts mid-loop the tool must not run again; it returns its recorded result. The same guarantee as any activity, applied to something the model decided rather than the developer.

03

Human in the loop

“I am about to refund €4,200 — confirm?” is one bounded wait that survives deploys. In a handler you cannot await; you store state and let a webhook find it again.

The limit, stated

Durable does not orchestrate Symfony AI’s inner loop — Agent::call() runs its own tool round-trips. What Durable bounds is the turn: one decision, its effects, an optional approval, then again.

Swap the backend, keep the workflow

A core that needs only psr/cache, an optional framework integration, and interchangeable backends — in-memory for tests, Temporal or SQL for production. The command changes; the workflow code does not.

gplanchat/durable

The library. Workflows, activities, timers, event journal. Exactly one runtime dependency: psr/cache. No framework.

required gplanchat/durable-bundle

The Symfony integration. Autoconfigures workflows and activities, wires Messenger transports, adds worker commands and a profiler panel. Symfony 6.4, 7 or 8.

optional gplanchat/durable-plugin

The Sylius admin dashboard for tracking durable workflows. Registers an entry in the Sylius admin menu. It observes rather than runs: it pulls the bundle in and leaves the backend choice to you.

The Temporal driver. Speaks gRPC to a Temporal cluster directly; no official PHP SDK, no RoadRunner. Requires ext-grpc.
